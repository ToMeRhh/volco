# Volco WebSocket Simulator

A minimalistic web-based simulator to test the Volco application without physical hardware.

## How to use

1.  **Start Volco** on your Windows machine.
2.  Go to the **Connection** tab in Volco settings.
3.  Select **WebSocket** as the connection type.
4.  Ensure the port matches (default: `8765`).
5.  Open `index.html` in your web browser.
6.  Click **Connect** in the simulator.
7.  Move the sliders and click the buttons to see Volco react!

## Controller types

Pick one before connecting:

- **LED controller (current hardware):** 5 sliders and 3 buttons with LEDs (LED, LED, LED pair). It behaves like the real hardware.
- **Screen controller:** 5 sliders and 4 buttons, each with a 128x64 screen that draws layout 1 (top line, icon, name). A preset change slides all screens together.

Auto-reconnect retries every 3 seconds.

## Protocol Implementation

The simulator speaks the same protocol as the firmware: it sends Hello (at connect, on HelloRequest, and when the PC comes back after a silence), Alive, Slider and Button, and it handles Led, Screen, Begin, Commit, HelloRequest and Heartbeat. The frame format and the message table are in the protocol section of `firmware/README.md`.

- **Host timeout:** if the PC sends nothing for 3 seconds, LEDs go off and every screen shows "NOT CONNECTED".
- **Begin/Commit:** updates are held after Begin and applied together on Commit (or after 500 ms without one), like the firmware.
- **Not simulated:** screen text uses the browser's fonts rather than Arimo, so it is close but not pixel-exact, and dimming, switching off and pixel shift are not simulated.
- `icons.js` holds the icon bitmaps and is generated by `firmware/tools/gen_assets.py`; do not edit it by hand.

## Controller config

The simulator keeps one controller config, like the firmware (spec §10 of `docs/design/controller-config.md`):

- **Hello** reports chip 1, firmware `sim`, and the stored config's state and CRC. Its sliders and buttons come from the stored config, or from the selected controller type when none is stored.
- **ConfigRead** returns the stored bytes; a **config write** follows the firmware's receiver rules. Validation decodes the blob (with the schema's limits and NUL checks) and checks the counts and the screen rules (bus, address, duplicates); pins aren't checked. After OK the simulator "reboots": it drops the connection for a second and comes back with the new hardware.
- The config is kept in the browser's `localStorage`; **Clear config** forgets it (and reboots).
- The logic is in `config.js`, the schema in `volco_config_descriptor.js` (generated from `proto/volco_config.proto`), and protobufjs loads from jsDelivr. Offline, config frames are ignored and the status line says so.

Tests (Node 22): `cd tools/simulator/test && npm ci && node --test`. After a change to the proto, regenerate the descriptor with `node gen_descriptor.mjs`; CI checks it is current.

## Troubleshooting

- Ensure Volco is running and WebSocket is selected.
- If you change the port in Volco, you must also change it in the simulator.
- Check the browser console (F12) for connection errors.
