# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Test

The .NET tests run in GitHub Actions CI (`.github/workflows/build.yml`):

```bash
# Run tests only on any branch (default — use this)
gh workflow run build.yml --ref <branch-name>

# Check CI status
gh run list --branch <branch-name> --limit 3
```

**IMPORTANT — build job rules:**
- Pushing to any branch, `main` included, automatically triggers tests only. The build/publish job never runs on push; it is manual only.
- `gh workflow run` (workflow_dispatch) triggers tests only by default. **Never trigger the build on a branch unless the user explicitly asks.** If they do ask, use:
  ```bash
  gh workflow run build.yml --ref <branch-name> --field run_build=true
  ```

CI runs tests on Ubuntu (net8.0) and builds/publishes on Windows (net8.0-windows10.0.22621.0, win-x64) with `dotnet publish` (single-file, self-contained, trimmed with `TrimMode=partial`; no msbuild). Trimming turns reflection-based System.Text.Json off, so config.json goes through the source-generated `Volco.Core.Config.ConfigJsonContext` (a new config type needs a `[JsonSerializable]` there if serialized on its own, and enums take `JsonStringEnumConverter<T>`). There are two test projects, both run by the Linux job: `tests/Volco.Core.Tests/` (xUnit 2) and `tests/Volco.App.Tests/` (Avalonia headless, xUnit v3). `global.json` pins SDK 10.0.100 (needed by the Avalonia analyzers); every project still targets net8.0 / net8.0-windows10.0.22621.0, and both workflows install the 8.0.x and 10.0.x SDKs.

**Firmware** (ESP32, in `firmware/`; needs PlatformIO Core >= 6.1.19 for the pinned pioarduino 55.03.38 platform, and a host `g++` for the native tests):
```bash
cd firmware && pio run -e esp32              # build
cd firmware && pio run -e esp32 -t upload    # flash (config in NVS survives)
cd firmware && pio device monitor   # serial monitor
cd firmware && pio test -e native   # host-side tests of firmware/lib (no hardware)
~/.platformio/penv/bin/python firmware/tools/gen_config_vectors.py  # regenerate firmware/test/golden/config.txt after a proto change
bash firmware/scripts/firmware_id.sh  # the firmware build id (hash of the firmware's sources)
~/.platformio/penv/bin/python firmware/tools/config_tool.py --port P read|write preset.json  # a controller's config (guarded port)
python3 firmware/tools/gen_assets.py  # regenerate icons and fonts (needs Pillow >= 10)
```

The `firmware-test` CI job runs `pio test -e native`, checks the firmware id and the config vectors, self-tests `scripts/manifest.py`, and builds the `esp32` environment with `VOLCO_FW_VERSION` = the build id; it uploads `.pio/build/esp32/dist/` (the four parts and `firmware-manifest.json`) as the `firmware-esp32` artifact and outputs the id. The Windows `build` job (`needs: firmware-test`) downloads it into `src/Volco.Windows/Firmware/esp32/`, which is embedded in `Volco.exe`, and publishes with `-p:RequireFirmware=true -p:VolcoFirmwareBuildId=<id>`, so the build fails without the firmware or with another build's. `firmware-test` also compiles `Volco.Windows` on Linux (`-p:EnableWindowsTargeting=true`) with that firmware embedded and `RequireFirmware`, and checks that a mismatched build id fails, so Windows-only code, the embedded resource names and the build-id check break on every push. `release.yml` runs version → firmware → release and attaches `volco-firmware-esp32-<version>.zip` with `THIRD-PARTY-NOTICES.txt`, `OFL.txt` and `relink/` (the LGPL relink bundle from `firmware/scripts/relink_bundle.py`: the firmware's link inputs as objects and the exact link command). `gen_assets.py` regenerates the firmware icons and fonts, the C# `ScreenIcon` enum and the simulator's `icons.js` and `fonts.js` from `firmware/assets`; its outputs are committed.

## Architecture

Volco is a Windows system tray app that controls PC audio via an external hardware controller (ESP32 with sliders and buttons). The app is split into three real source projects (`Volco.Core`, `Volco.App`, `Volco.Windows`) plus two test projects (separate `.csproj`s, not `<Compile Remove>` tricks), plus the firmware:

### `src/Volco.Core/` — platform-neutral, `net8.0`, builds and tests on Linux

No UI, no platform APIs. Holds the protocol, config, input, and orchestration layers:
- `Communication/` — `IControllerConnection` (transport interface: Serial, UDP, WebSocket, all bidirectional `Send`/receive; its `TransportStatus` (`Closed`/`Open`/`Failed`) is a port or socket fact, never "connected"), `ProtocolParser` (stateful byte stream parser; finds `0xAA` start markers, validates XOR checksums, emits `ControllerMessage` events), `ProtocolEncoder` (static class building outbound frames: HelloRequest, Heartbeat, Led, Screen, Begin, Commit, and the config read and write bursts), `ControllerDisplay` (decides what each button shows: its LED value or screen content, from its action in the live mode; for 1.5 s after a press a button shows what it did: an error icon and why, or a fast-flashing LED, when it did nothing; the pressed action on a screen, or a double LED blink, for a double press or hold; a Play/pause's expected state at once; a failing script on any slot, custom-actions spec §11).
- `Input/` — `ButtonPressDetector` (classifies raw press/release into single, double, long press; the controller-wide `buttonTiming` values, defaults 500 ms hold and 300 ms double-press window, and a button with no double-press action in the live mode doesn't wait (window 0); a release without its press fires nothing, and `Reset()` drops every gesture in progress), `SliderProcessor` (maps 12-bit ADC values 0–4095 to volume, linear: no curve, dead zone or invert; coalesces at 20ms intervals), `Actions/` — `ActionFactory` maps button config to `IButtonAction` implementations, and `ActionValidator` lists an action's problems by field (device, mode, file path, start-in folder; the action dialog shows them, the runtime runs no invalid action); `Config/SliderTargetValidator` is the slider target's rule (an apps slider needs an app).
- `Audio/` — `IAudioEngine`, the platform-neutral audio interface (the seam that lets everything else build and test on Linux), plus its DTOs: `AudioDevice`, `DeviceRef`, `AudioFlow` (`Render`/`Capture`). There is no `AudioRole` in this API — Core Audio's Console/Multimedia/Communications roles never varied per call site, so the public surface only exposes flow (`GetDefaultDevice(AudioFlow flow)`, no role parameter). `AudioRole` still exists, but only as an internal detail of the Windows engine. `GetSessionPeak(instanceId)` reads a session's live peak level (0–1) for the target dialog's app meters; a session carries its display name and icon path (`AudioSessionInfo`).
- `Config/`, `Updates/` — `ConfigManager`/`ConfigMigrator`; `BuildInfo`, `GitHubUpdater` (the latest release from the public GitHub Releases API, unauthenticated; only its `Volco.exe` asset) and `UpdateInstaller` (downloads it and swaps it in after exit).
- `Devices/` — `DeviceDisplay`, the display name (nickname, else friendly name) and icon of a device, used by the OSD, the pickers and the controller screens.
- `Controller/` — the controller config: `ControllerConfigCodec`/`ControllerConfigValidator`/`ControllerPresets` (the protobuf blob), `ControllerConfigService` (owned by `VolcoRuntime`: reads the controller's config, saves one with retries, implied OK and confirmation, keeps the mirror, and runs the one automatic read), and `ControllerBannerLogic` (spec §8.3: what the Controller page shows after a Hello, as a pure function).
- `Firmware/` — `FirmwareManifest`/`FirmwareImage`/`FirmwareCatalog` (the bundled firmware, from an `IFirmwareSource`; a manifest part overlapping NVS is rejected), the `IFirmwareFlasher` seam, and `FirmwareService` (one probe or flash at a time: `VolcoRuntime.SuspendConnection()` frees the port and blocks every restart, a dialog port is saved while suspended (on the config's thread, the UI thread in the app), then the bundled build's Hello is awaited).
- `Diagnostics/` — `Volco.Core.Diagnostics.AppLog`.
- `Media/`, `Programs/`, `Scripts/` — the custom button actions (spec `docs/design/custom-actions.md`): `IMediaSessions` (seam: the system's media sessions, play/pause, next, previous, stop to the current app or an app id), `IProgramLauncher` (seam: is an exe running, start through the shell, bring to front, poll a watched set), `ProgramOpener` (front if running, else start, 5 s launch debounce; `LnkFile` reads a shortcut's exe target), `CommandPath` (Windows path text parsed the same on every OS, display names), `ScriptInterpreters` (.bat/.cmd → cmd, .ps1 → pwsh else powershell, .py → py else python, .js → node, .exe, else the file association) and `ScriptRunner` (hidden runs through `IProcessStarter`/`SystemProcessStarter`, Ignore or StartAnother while running, a 12 × 125 ms failure flash, never kills; state per action object). `Runtime/ActionStatus` (`IActionStatus`) is what `ControllerDisplay` reads for them: an LED lit while the media target plays, the program runs or the script runs (blinking on failure); screens say `PLAYING`/`PAUSED`, `RUNNING`, `FAILED` over the name; a playing media target shows the animated equaliser icon, a paused or stopped one the frozen bars (`docs/design/playing-indicator.md`).
- `Runtime/` — `VolcoRuntime`, the UI-facing orchestrator. It owns transport construction/`Connect()`/restart-on-config-change, routing `IControllerConnection.MessageReceived` to `SliderProcessor`/`ButtonPressDetector`, `ActionFactory` dispatch on detected presses, the pending-mute-OSD correlation, and `PushControllerState`, which delegates to `ControllerLink`. `Disconnect()` (the Controller page's and tray's Disconnect) drops the transport and starts none, even on a connection-config change, until `Connect()` or `Reconnect()`; it is not persisted. `ControllerLink` owns the controller protocol session: HelloRequest retries, the Hello handshake (nothing is pushed before it), keepalive, dedup against the last-sent content per button, and Begin/Commit bursts for mode changes. It computes, dedups and enqueues under its lock but sends through a single-consumer outbox outside it, dropping frames for a retired connection. It exposes only `Volco.Core` types (`IAudioEngine`, `ConfigManager`, `LinkStatus`, etc.) — nothing UI or Windows-specific leaks through it. It also runs the hardware test mode (spec §8.5): `EnterTestMode()` returns a handle; while it is held, Slider and Button messages raise `RawInput` and reach neither audio nor actions, each press moves its button's test indicator on (`Runtime/TestMode.cs`: a single LED toggles, a pair goes A, B, A…, a screen counts presses; `RawInputEventArgs.Presses`); the runtime ends it itself on Detach, connection replacement and dispose. Open a program and Run a script run only for presses whose frame came over USB serial (`_pressOverUsb`, captured per button at the press frame) or from the settings UI's Test (`Execute(action, ActionOrigin)`); over UDP or WebSocket they are refused and logged (custom-actions spec §7). `CustomActionServices` (media, launcher, process starter; each optional) is the runtime's last constructor argument, and `ActionStateChanged` tells the UI that one of them changed. `LinkStatus` (`Runtime/LinkState.cs`, spec `docs/design/link-state.md`) is what the UI calls connected: `Connected` only after a Hello with this app's protocol version, else `Searching`, `PortBusy`, `NoAnswer`, `Incompatible`, the user's `Disconnected`, or `Waiting` (an expected gap: `ExpectInterruption` handles held by a firmware probe or flash, the connect grace of a start or reconnect, a config save); it is a pure function of the transport, the session, the silence, the interruptions and the save (`LinkStateLogic`), raised as `LinkStatusChanged`. Slider calibration (spec `docs/design/slider-calibration.md`): `SendCalibrate(index, CalibrateAction)` sends a `0x8E`, `CalibrationChanged` raises each `CalibrationMessage` (`0x09`), `GetCalibration(index)` is the last `SliderCalibrationState` per slider (each Hello forgets them, raising `CalibrationChanged` with a null state, and queries every slider; a report of a sweep no hold waits for gets a Cancel), and `HoldSlider(index)` returns a handle that keeps a slider's moves away from audio (`IsSliderHeld`) until the sweep's ending report arrives or the link drops; a sweep the runtime holds is cancelled on connection replacement and dispose. Firmware helpers (spec `docs/design/hardware-page.md` §9; an older firmware doesn't answer, so each no-ops or reports no answer): `StartPinWatch(PinWatchRole)` returns a handle (one watch at a time; while one is on (`IsWatchingPins`), Slider and Button messages raise only `RawInput`, as in a test; a new one replaces it; it is renewed every `PinWatchRenewal`, 10 s, and re-sent after each Hello of the session; disposing it, or the runtime, sends the Stop), `PinActivity` raises each pin the controller reports for the current connection, `ScanI2cAsync(sda, scl)` waits `I2cScanTimeout` (3 s) for the `I2cScanResult` of those pins (addresses; null on no connection, no answer or dispose), `DrivePin(pin, high, duration)` sends a PinDrive, and `TryLights(steps)` plays `LightTry.Steps` (a single LED lit, unlit, lit, 300 ms each; a pair A lit with B unlit, then B lit with A unlit at 700 ms, 600 ms each; each step drives its level) as timed PinDrives, a new call cancelling the unsent steps of the last. Constructed headless (e.g. with a fake `IAudioEngine`), the whole app's behavior is driveable from Linux tests with no UI process.

### `src/Volco.App/` — Avalonia 12 UI, `net8.0`, builds and tests on Linux

The whole UI as portable Avalonia code, a view over `VolcoRuntime`. What each screen does is in the specs: `docs/design/controller-page.md`, `controls-page.md`, `hardware-page.md`, `link-state.md`, `custom-actions.md`, `slider-calibration.md`.
- **Rules.** **`Volco.App` and `Volco.Core` must stay platform-free** (no `DllImport`/`LibraryImport`, no `Windows.*`/`Microsoft.UI.*`, no CsWin32); `tests/Volco.App.Tests/ArchitectureTests.cs` enforces it by reflection (no P/Invoke, no Windows assembly references; `DllImport`, `LibraryImport` and CsWin32 all compile on Linux, so compiling alone cannot catch them), and the Linux compile catches WinRT and Windows SDK projections. Every surface (tray, sidebar, Controller page) reads only `VolcoRuntime.LinkStatus`, worded by `LinkText` ("Connected" only for a matching Hello, "Disconnected" only for the user's Disconnect; the physical layer is "plugged in", "port", "listening"); `ArchitectureTests` fails if `Volco.App` mentions `TransportStatus`. Button modes are not the Controller page's layout presets (`ControllerPresets`), which keep that name.
- **Seams.** Everything OS-specific comes in through `IAudioEngine` (Core), `IWindowEffects` (App, `MakeClickThrough` for the OSD) and the optional ones (`IStartWithSystem` for General's "Start Volco when you sign in", null hides it; flasher, firmware, media, launcher; `IAppIcons` for an app's icon, null shows a letter tile, reused by `AppIconLookup`, one per run, for an apps slider's icon on its tile, the inspector and the OSD), bundled as `PlatformServices` and handed to `VolcoAppHost.Run` with the head's Avalonia backends (`Volco.App` references no backend package).
- **Startup and shutdown.** `VolcoAppHost.Run` parses `LaunchOptions` (`--background`: a sign-in start stays in the tray; otherwise the settings window opens) and takes the `SingleInstance` claim (a per-user named mutex plus a named pipe): a later start asks the running Volco to show its window (or, in the background, does nothing) and exits. `CompositionRoot` owns startup/shutdown, the tray and the windows; Exit and the updater's restart wait for a firmware write or a config save through `ExitGate`, OS logoff never waits.
- **Tray.** The icon turns red (`Assets/volco-disconnected.ico`) while `LinkStatus.IsDown` (not Connected and not an expected wait), with a tooltip that says why (`TrayStatus`); its menu has Connect/Disconnect. A controller that needs the user adds a tooltip line, a menu item that opens the Controller page and, when the link is not down, the attention icon (`Assets/volco-update.ico`).
- **Settings window.** Two pages, General and Controller (tag `controller`; `ShowPage("controls")` maps to it), in a `PageHost` (`TransitioningContentControl`; its 150 ms crossfade is off when `StageTransitions.Enabled`, set by Volco.Windows from the Windows animation setting, is false). The sidebar has the controller status line (`ControllerStatusViewModel`, the §4.1 table in `DeviceCard` and its `StatusLevel`, over `ControllerBannerLogic`'s banner, the link and the firmware state), the version, a GitHub link and the notices (`AboutViewModel`); below 1000 px wide it shows icons only and opens over the page on hover. A status that needs the user is also a `StatusBanner` on every page. A firmware install, update or check, or a save, runs in the modal `ProgressDialog` (`ProgressDialogViewModel`) above every other dialog. The I2C buses, pin, Connection, Compare, Reinstall, calibration and leave-prompt dialogs are window-level overlays in `SettingsWindow`.
- **Controller page.** `Views/Stage/StagePage` over `ControlsViewModel` (reusing `SlidersViewModel`/`ButtonsViewModel` and their items): a drawing of the controller from the last Hello, slider tiles (`Controls/SliderTile`) then button tiles (`Controls/ButtonTile`) in the edited mode's frame and tabs (`ModeTabReorder`), both grids `Controls/FillWrapPanel`, and the title row's + Add, Controller settings and Test (the hardware test, spec §8.5; leaving the page or hiding the window ends it). Dragging a tile's grip (`Views/TileSwapDrag`) or its context menu's Swap (`ControlsViewModel.Swap`/`SwapChoices`) swaps two sliders' targets and names (Reverse direction and the other Hardware fields stay with the physical slider; `VolcoRuntime.ReapplySlider` sets each new target to its slider's last position) or two buttons' actions in the edited mode. Button previews come from `ControllerDisplay.For` with the runtime's press feedback and announce (`Runtime/IButtonFeedback`, implemented by `VolcoRuntime`), as the controller's do. `HardwareViewModel` draws the draft's controls with their wiring. A pin field opens the pin dialog (`Views/Hardware/PinDialog` over the `PinFieldViewModel`, a window-level overlay above the I2C buses dialog through `HardwareViewModel.PinDialog`: every GPIO at once, eight to a row by number), which runs Detect (`StartPinWatch`: moving a slider or pressing a button marks that pin by colour, "moving now" for `PinFieldViewModel.ActivityHold` after each report, then "moved before", and never picks it; the watch ends when the dialog closes, the tile changes, the window hides or the page is left), each bus of the I2C buses dialog has Find screens (`ScanI2cAsync`: the addresses that answered and which buttons use them) and a button's Hardware section has Try the lights (`TryLights`, through PinDrive for saved and unsaved pins alike). `ControllerViewModel` is the logic under the page: the draft, its problems (`DraftProblems`), Save/Discard through `ControllerConfigService`, inline confirmations (`Confirmation`, red only when destructive), the setup chooser, Install/Update/Check firmware and test mode. The save rule (spec `docs/design/slider-feel-settings.md`): a tile's Hardware section and Controller settings are a draft committed by Save (the button always reads Save; a new control's prompt is "Save to set it up"), and Hold after and Double press within, which Volco stores in `config.json` (`buttonTiming`), are part of that draft (`HoldMs`/`DoublePressMs`, `ControllerDirty`/`TimingDirty`): a timing-only Save writes `config.json` at once, sends nothing and shows no restart note, and a mixed save commits them when the controller confirms. Controller settings has Screens, Sliders (Smoothing Low/Normal/High/Custom; Fine tune: Smoothing weight, Ignore changes below), Buttons (Hold after, Double press within; Fine tune: Debounce) and Wi-Fi; Read sliders every is not in the UI (its proto field is kept). Leaving the page with unsaved changes asks first (`LeavePromptViewModel`); hiding the window doesn't.
- **Inspector** (`Views/Inspector/`). Two sections: Controls (or Actions), then Hardware, whose edits go to the controller draft. A slider's Controls card is its target only, and its Hardware section holds the pin, Reverse direction, Auto-calibrate with the calibration state and Re-calibrate, a read-only "Smoothing (all sliders)" link to Controller settings › Sliders, and Remove; a button's Actions are its gestures and the Light or Screen row, with no Timing. Hardware's top never moves: `StagePage.InspectorTopHeight` is the tallest tile's top section, measured one tile at a time, as it is (no sub-section is opened for it), on an unseen `IsProbe` copy of its `TileInspector` that is emptied afterwards (`StagePage.InspectorProbe.cs`), since every control of a page is styled anew when it is shown again. Rows are cards (`Border.InspectorRows` over `Controls/CardRows`; `Border.CardBody` for a group's body, `Border.Nested` for a sub-option), and a non-trivial setting has a `Controls/HelpTip` "?" before its label. A button's gesture rows are `ActionSlotViewModel`s. Re-calibrate opens `Views/Hardware/CalibrationDialog` (`CalibrationDialogViewModel`), which holds the slider with `HoldSlider`.
- **Dialogs.** The action dialog (`Views/Dialogs/ActionDialog`, `ActionDialogViewModel`) edits the picked action's settings (`Controls/ActionSettings`) on a draft that Done validates and writes; `ActionCatalog.ChoicesFor(ActionAvailability)` disables the actions whose `PlatformServices` service (`Media`, `Launcher`) is missing. The target dialog (`TargetDialog`, `TargetDialogViewModel`) lists outputs, inputs and apps; Done checks `SliderTargetValidator` and takes the apps off other sliders. Both search with `ViewModels/Search/FuzzyMatcher` through `DialogSearch`, keep the focus inside and close without writing on Escape or a click outside. The device dialog (`Views/Dialogs/DeviceDialog`, `DeviceDialogViewModel` over `DevicesViewModel.ItemFor`) sets a device's nickname and icon (`config.devices`) as they are edited; it opens over the dialog that asked for it (`ControlsViewModel.OpenDeviceDialog`, `DeviceOverlay`), which re-reads the names through `IDeviceNamesListener`. The I2C buses dialog is `Views/Hardware/I2cBusesDialog` (`I2cBusesViewModel`). Every device name shown comes from `Volco.Core.Devices.DeviceDisplay`.

### `src/Volco.Windows/` — `net8.0-windows10.0.22621.0`, the shipping `Volco.exe`

`WinExe` with `<AssemblyName>Volco</AssemblyName>`, referencing `Volco.Core` and `Volco.App`. Entry point is `Program.Main`: it hooks the AppDomain/TaskScheduler exception loggers, builds the `AudioEngine`, and calls `VolcoAppHost.Run(args, UseWindowsBackends, () => new PlatformServices(engine, ready, new Win32WindowEffects(), …))`; `UseWindowsBackends` is HarfBuzz + Win32 + Skia, from the `Avalonia.Win32`/`Avalonia.Skia`/`Avalonia.HarfBuzz` packages rather than `Avalonia.Desktop` (which would also bundle the Linux and macOS backends); it renders in software (`Win32RenderingMode.Software`), and the `DropAngle` target leaves ANGLE (`av_libglesv2.dll`) out of the publish. Holds the Windows implementations of the two seams, in namespace `Volco.Windows.*`:
- `Audio/AudioEngine` — the real Core Audio engine. Owns one dedicated MTA thread and a struct-command work queue; all COM activation, registration, and writes happen on that thread. `Start()` returns `bool` (whether the engine came up), which `VolcoRuntime` uses to skip config migration if audio isn't ready.
- `Audio/DeviceRegistry` — caches every live endpoint and its COM objects, kept current by `IMMNotificationClient` instead of re-enumeration (a rename in Windows re-reads the friendly name and raises `StateChanged`); it also reads each endpoint's form factor (`PKEY_AudioEndpoint_FormFactor`), which picks a device's default icon.
- `Audio/SessionRegistry` — caches every live per-app audio session across all render devices, driven by `IAudioSessionNotification`; volume writes are an O(1) dictionary lookup, never an enumeration.
- `Audio/DefaultDevicePolicy` — switches the Windows default output device via the undocumented `IPolicyConfig` COM interface.
- `Platform/Win32WindowEffects` — `IWindowEffects` via Win32 extended styles; with `Program`'s `AllowSetForegroundWindow` (so a second start can bring the running window forward) and `SystemParametersInfoW` (`SPI_GETCLIENTAREAANIMATION`, which sets `StageTransitions.Enabled`), the only UI P/Invoke in the repo.
- `Platform/RunKeyStartWithSystem` — `IStartWithSystem` through `HKCU\…\CurrentVersion\Run` (`"Volco.exe" --background`), honouring Task Manager's `StartupApproved` off switch; the registry is the only record.
- `Media/MediaSessions` — `IMediaSessions` over WinRT's `GlobalSystemMediaTransportControlsSessionManager` (requested in the background; a snapshot rebuilt on every session event); `Programs/ProgramLauncher` — `IProgramLauncher` (process name then `QueryFullProcessImageName`, a 2 s poll of the watched exes, `AttachThreadInput` + `SetForegroundWindow`, `FlashWindowEx` when Windows refuses). Both are handed to the app through `PlatformServices`.
- `Firmware/EspDotNetFirmwareFlasher` — `Volco.Core.Firmware.IFirmwareFlasher` over EspDotNet (the only project referencing it): ROM bootloader via DTR/RTS, chip check, the stub at 460800 baud when possible, MD5 probe of the app region, part-by-part writes with MD5 verify (Install also writes 0xFF over the manifest's NVS range; Update never touches it), reset. `Firmware/EmbeddedFirmwareSource` reads the embedded `Firmware/esp32/*`.
- `app.manifest` (asInvoker, PerMonitorV2 DPI) and `volco.ico`.

**Data flow:** Controller sends binary frames → `IControllerConnection` receives bytes → `ProtocolParser` extracts `ControllerMessage` → `VolcoRuntime` routes to `SliderProcessor`/`ButtonPressDetector` → `IAudioEngine` changes Windows audio state. For state feedback, `ProtocolEncoder` builds frames → `IControllerConnection.Send()` pushes to controller.

### ESP32 Firmware (`firmware/`)

PlatformIO / Arduino framework / C++17. `src/` (`main.cpp`, `config.h` (fixed constants), `config_store.*`, `config_session.*`, `transport.*`, `indicators.*`, `screens.*`, `slider_ends_store.*` (the ends in NVS: one blob under key `ends2` in namespace `volco_ends`, holding pin-keyed entries), `pin_helpers.*` (the watch's sampling, the I2C scan and PinDrive on the hardware)) plus pure-C++ libraries in `lib/` (`volco_protocol`, `volco_config`, `volco_bidi`, `volco_screen_state`, `volco_render`, `volco_slider_ends` (a slider's learned travel ends, from the smoothed reading), `volco_calibration` (one slider's calibration: Auto-calibrate, the Re-calibrate sweep, when a Calibration report is due, and the pin-keyed NVS entry codec), `volco_pin_helpers` (the rules of Detect, Find screens and Try the lights: which pins a watch samples per role, when a pin is worth reporting, how a scan reaches a pin pair, which pins may be driven)) that are tested on the host with `pio test -e native`; `firmware/README.md` explains the code structure. Rendering uses Volco's own 1-bit canvas, with U8g2 only as the SSD1306 driver.

The controller config schema is `proto/volco_config.proto` (proto2; limits in `proto/volco_config.options`; presets in `proto/presets/`). It generates nanopb code for `firmware/lib/volco_config` (decode, validation, chip table, CRC, chunked receiver) and C# for `Volco.Core/Controller` (codec, validator, presets). Both are checked against the same generated vectors, `firmware/test/golden/config.txt`. A slider's Reverse direction is `Slider.reverse` (field 3): the firmware applies `4095 − v` last, to every slider value it sends (`sliderOut` in `volco_runtime.h`: main loop, after a Hello, end of a sweep), while Calibration reports and the pin watch stay raw; the simulator's `calibration.js` does the same, the Re-calibrate dialog mirrors its bar for a reversed slider, and Compare lists a reverse difference. Deferred review findings are listed in the spec's §14.1. The app runs the config session (`ControllerConfigService`), driven by the Controller settings page.

The firmware reads its hardware layout (sliders, buttons and their indicators, I2C buses 0-3, of which 2 and 3 are software I2C), the optional Wi-Fi/UDP link and the screen and input settings from the controller config stored in NVS (`config_store`, spec §6.6), never from `config.h`; `toRuntime()` turns it into the flat `RuntimeConfig` that `src/` uses. A table's order is the input number the app sees. An empty NVS boots on built-in defaults (no inputs); Volco's Controller page stores a config, and so does `firmware/tools/config_tool.py --port P write preset.json` for firmware work without the app (the board reboots into it; `read` prints the stored one). USB serial is always on; UDP runs alongside when the config enables it, and the controller answers on whichever transport last sent it a valid frame (spec §5.5). `firmware/tools/hello_check.py --port <port> --sliders N --kinds …` resets the board and checks its boot Hello; it refuses any USB device but the DIY board's CH340 (`1a86:7523`), and tty numbering can change after a replug, so always let it check first. The firmware has no notion of mute or devices; it reports raw input and its hardware (Hello), and renders the LED values and screen descriptions the PC sends.

### Wire Protocol

Bidirectional binary protocol. Frame: `0xAA | length | type | body | XOR checksum`. The high bit of `type` is the direction; integers are big-endian. Full details (Screen body, behaviour rules) are in `firmware/README.md`.

| Type | Name | Direction | Body |
|---|---|---|---|
| `0x01` | Hello | controller→PC | version, chip, firmware id, config state and CRC, slider count, button count, one kind per button (0 none, 1 LED, 2 LED pair, 3 screen) |
| `0x02` | Alive | controller→PC | none (keepalive) |
| `0x03` | Slider | controller→PC | index + 16-bit value |
| `0x04` | Button | controller→PC | index + pressed |
| `0x05` | ConfigData | controller→PC | seq, total, offset, CRC, one chunk of the stored config |
| `0x06` | ConfigResult | controller→PC | seq, code, item, field (the answer to a config write) |
| `0x07` | PinActivity | controller→PC | pin (a watched pin moved or was pressed) |
| `0x08` | I2cScanResult | controller→PC | SDA, SCL, count, count addresses |
| `0x81` | HelloRequest | PC→controller | none |
| `0x82` | Heartbeat | PC→controller | none (keepalive) |
| `0x83` | Led | PC→controller | button + value |
| `0x84` | Screen | PC→controller | button, transition, layout, top, icon, flags, main text |
| `0x85` | Begin | PC→controller | none (hold updates) |
| `0x86` | Commit | PC→controller | none (apply held updates together) |
| `0x87` | ConfigRead | PC→controller | seq |
| `0x88`/`0x89`/`0x8A` | ConfigWriteBegin/Chunk/End | PC→controller | seq + total and CRC / offset and data / none |
| `0x8B` | PinWatch | PC→controller | role (0 stop, 1 analog, 2 button) |
| `0x8C` | I2cScan | PC→controller | SDA pin, SCL pin |
| `0x8D` | PinDrive | PC→controller | pin, level (0/1), duration (u16 ms) |
| `0x8E` | Calibrate | PC→controller | slider index + action (0 query, 1 start sweep, 2 done, 3 cancel) |
| `0x09` | Calibration | controller→PC | slider index, flags (bit 0 learned, 1 sweeping, 2 auto), low and high ends (u16 each); the answer to every Calibrate, and sent as the ends widen |

`Communication/ControllerDisplay` decides what each button shows (its LED value or screen content) from its action in the live mode. A single LED and an LED pair differ: a pair shows a toggle's side (1 = A, 2 = B) and the live mode's position, while one LED is lit on the toggle's B and while a "Go to mode" target is live. For `AnnounceSteps` link ticks (~1.5 s) after a mode change, a button with a mode action announces it: one LED blinks, and a screen that shows another action flashes the live mode. The firmware needs no change for this, because the link re-sends on each tick. `Runtime/ControllerLink` runs the session: Hello, keepalive, dedup, the Begin/Commit bursts for mode changes, and the announce ticks. (The old `0x03` mute state, `0x04` active device and `0x05` feedback messages are gone with protocol v1.)

### Web Simulator (`tools/simulator/`)

`index.html` is a 3D controller simulator (three.js; a home-office desk) that speaks the full protocol and config session to Volco over WebSocket. Open it directly in a browser; there is no build step: three.js (pinned 0.170.0, through an import map and one inline module that publishes `window.VolcoThree`) and protobufjs load from jsDelivr, and every other file is a classic script that also loads under Node. The logic has no DOM: `protocol.js`, `link.js` (the firmware Link, with fault hooks), `config.js` (the config session; the blob is kept in `localStorage`), `layout.js` (the builder's model, presets, and ESP32 pin allocation that passes the app's validator), `oled.js` (a port of `volco_render`, `volco_bidi` and `volco_screen_state`, pixel-identical through `fonts.js`), `calibration.js` (answers Calibrate: a sweep reports the range the user drags through, learned once it spans 1000 codes), `pinhelpers.js` (answers PinWatch with the pin of a slider dragged or a button clicked, I2cScan with the screens its config's buses have, and PinDrive by lighting the LED on that pin for the duration) and `demo.js` (demo mode, and which output a Volco screen shows, for the sound waves). The scene is `stage.js`, `room.js` and `device.js`; the UI is `connection.js`, `builder.js` (a draft with Apply and Auto-save) and `devtools.js` (frames, config, faults), wired by `app.js`. While no WebSocket is open the board runs in demo mode. `tools/simulator/test` holds the Node tests (`npm ci && node --test`), run by the `simulator-test` CI job; they use `firmware/test/golden/frames.txt` and `render.txt` (layout-1 bitmaps from the firmware renderer; regenerate with `VOLCO_WRITE_GOLDEN=1 pio test -e native -f test_render`), and `gen_descriptor.mjs` regenerates `volco_config_descriptor.js` after a proto change.

## Numbering sliders and buttons

- **Code, the wire protocol, the firmware and the config files number sliders and buttons from 0:** the input number, which is the position in `config.json`'s lists and in the controller config's tables, `SliderIndex`/`ButtonIndex`, and the index in every frame. Docs that describe those formats do too.
- **Everything a person reads numbers them from 1, as "Slider 1", "Button 1":** the settings UI (the Controller page, dialogs, toasts, the hardware test), messages (`ControllerDraft.Target`, `DraftProblems`), the controller's own test screen (`TestMode.Screen`), `VOLCO_BUTTON`, the app log's "Button N" lines, the simulator and prose in docs. Write `index + 1` where an index becomes a name. Log fields labelled `index=`/`Index=` stay the 0-based input. I2C buses keep their hardware numbers (0-3).

## Config

Runtime config stored at `%APPDATA%/Volco/config.json`. Managed by `ConfigManager` (load/save/change events; a debounced `RequestSave` still pending at exit is written by `FlushPendingSave` after the runtime is disposed). Includes connection settings, slider mappings, button modes and button actions, and on each apps slider `appPaths` (its apps' exe paths, only for their icons while they are not running; sessions are still matched by exe name; an optional field, no schema change). A slider's or button's **position in its list is its hardware input number** (`Index` is rewritten to match on save). Schema v8 adds the top-level `buttonTiming` (`{longPressMs: 500, doublePressWindowMs: 300}`, `ButtonTimingConfig`, controller-wide, edited in Controller settings › Buttons) and drops the per-button `longPressMs`/`doublePressWindowMs` and the slider `invert`/`curve`/`deadZonePercent` (Response is gone; reverse is now the controller's `Slider.reverse`); `ConfigMigrator.MoveButtonTiming` takes the first button's values, else the defaults, and a v7 file is stamped with `config.v7.bak`. Schema v7 renames presets to modes (`presets` → `modes`, each action's `presetId` → `modeId`, the actions `NextPreset`/`GoToPreset` → `NextMode`/`GoToMode`; mode ids such as `"default"` are kept, and new ones are `mode-<n>`); every older file passes through `ConfigMigrator.RenamePresetsToModes` on load, and v3–v6 files are stamped with a `config.v<n>.bak`. Schema v6 adds the custom action fields: `mediaApp` (`{id, name}`, null = the current app), `command` (`{path, arguments, workingDirectory, name}`) and `whileRunning` (`Ignore`/`StartAnother`). Schema v5 adds `controllerConfigBlob` (the mirror: base64 of the controller's config bytes, written only by `ControllerConfigService` on a confirmed save or an adopted read) and drops the serial baud rate (fixed at 115200). Schema v4 adds `devices` (per-device nicknames and icons) and `controller` (the last Hello's hardware summary). Schema v3: each button keeps its actions per mode (`buttons[i].actions[modeId]`, called presets until v7), and the toggle action carries its own A/B devices (`device`/`deviceB`); there is no global output pair. Devices are stored as endpoint IDs with the friendly name kept for display and fallback. `ConfigManager.Load` upgrades v1/v2 JSON to the v3 shape (v2 is rewritten with a `config.v2.bak`); v1's device-name resolution still runs in `VolcoRuntime.Start` once audio is up.

App log at `%APPDATA%/Volco/volco.log` via `AppLog` (async file writer with 500ms flush).
